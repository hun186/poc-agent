# SRAF operator E2E capability preflight — request boundaries

The existing authenticated superuser `GET /v1/operator-e2e/runtime-evidence` explicitly prepares and freezes the E2E backend plan. It is NOT part of normal FastAPI startup or a safe anonymous health check. It may contact real LLM servers, inspect or seed the dedicated E2E Elasticsearch fixture and should only be executed with operator authorization.

For `REQUIREMENT_E2E_EXTERNAL_MODE=live` and `auto`, direct Router/Report/Refiner probes already send a short READY request with a 10s client timeout. The Data Agent boundary uses a separate smolagents LiteLLMModel READY call with **`timeout=30`, `num_retries=0`**; these arguments are only for E2E capability selection, not production report generation. An unavailable boundary is a redacted probe failure: `live` rejects the plan; `auto` may freeze the documented semantic-mock E2E fallback, and that fallback must NEVER affect production jobs. `offline` does not send live model probes.

**Limitations:** Request timeout does not guarantee whole-operation termination; the authenticated HTTP harness still uses a 600-second *inactivity/read* timeout, not a 600-second absolute wall clock. Other ES and model operations may take additional time and eventual network cancellation is provider-dependent. No private Linux busy-Ollama preflight, Report Job, Agent, SQL/ES or DOCX acceptance was performed in GitHub Hosted CI. Operators must keep the normal, nonmutating baseline separate from E2E preflight and must not auto-run live fixture setup as diagnostics.


## 2026-10-30 Operator preflight re-entry/status (follow-up to #322)

An authenticated **superuser** may call `GET /v1/operator-e2e/runtime-evidence/status` to observe the current API process's operator runtime-evidence request. Response schema `sraf_operator_preflight_status_v1` contains only `state` (`NOT_STARTED`, `RUNNING`, `COMPLETED`, `FAILED`), `generation`, `elapsed_seconds` (monotonic) and fixed `scope=process_local_runtime_evidence_only`. No URL, token, model output, SQL or ES fixture details are returned. This is **not** a durable job, global/multi-worker state, release proof or an E2E FULL_LIVE result. `COMPLETED` means the runtime-evidence handler returned; inspect its actual acceptance payload separately.

The endpoint refuses a *second concurrent runtime-evidence call in this API process* with HTTP 409 `external_e2e_preflight_in_progress` **before entering the LLM/ES resolver**. It does not cancel an active probe. After the HTTP client disconnects or #322's 600s Linux client timer expires, status correctly remains `RUNNING` until the server operation actually exits. It is safe to poll status, not to assume client timeout stopped the server. Exception unwind records `FAILED` without persisting raw exception strings. On termination, the next operator request may enter; the immutable backend plan still prevents conflicting plans. This state is intentionally reset on API process restart and must not be used for multi-process coordination.

A genuine shared server-side monotonic deadline propagated through **all** LLM/ES boundaries, safe cancellation/fixture transaction semantics, and durable polling with `TIMEOUT` remain future independent work. Do not report these as implemented. No normal startup/Report Job/Schedule/Handoff/production timeout changes were made in this slice.


## 2026-10-30 Cooperative server deadline (post-#323)

The authenticated operator-only synchronous `GET /v1/operator-e2e/runtime-evidence` now scopes a **540-second monotonic cooperative budget** to each request, leaving headroom under the separate unmerged PR #322 proposal of a 600s Linux client wait. Ordinary API startup, normal report generation, LLM/ES use, Schedule/Handoff and Worker timeouts remain unchanged. Operator READY probes use the minimum of existing 10s/30s per-call limit and current remaining budget. Every E2E ES operation uses a new per-call `Elasticsearch.options(request_timeout=min(30s, remaining), max_retries=0, retry_on_timeout=False)` view, and deadline checkpoints run after every ES operation and before publishing an immutable E2E plan. Release provenance/root evidence now precedes any E2E backend plan preparation.

Once a provider **returns** after the deadline, the API fails closed with sanitized HTTP 503 `external_e2e_preflight_deadline_exceeded`; terminal superuser status is `TIMEOUT`. A stuck SDK is **not** forcibly terminated: the in-flight status becomes `RUNNING_OVERDUE` after 540s, and the process-local duplicate guard remains held until actual exit. Never interpret client disconnect, a timer or `RUNNING_OVERDUE` as remote cancellation. Dedicated ES fixture create/index operations that completed before a timeout are **not** automatically rolled back; future attempts must still verify fixture ownership, Mapping and dataset before plan acceptance.

This is a cooperative deadline and a truthful status/late-plan guard, **not** a hard 540s total stop guarantee, atomic fixture transaction, cross-process mutex, durable job/polling authority or FULL_LIVE acceptance. Private Linux busy-Ollama and real ES SDK timeout behavior still require separately authorized acceptance. No normal SRAF workload is run by this diagnostic change.


## 2026-10-30 Exact ES fixture revalidation and Linux same-host fencing

The operator-only live/auto ES acceptance fixture now uses *two* exact dataset attestations. Before mutating anything, verify dedicated index ownership and Mapping, count all documents and `mget` every expected ID; require `_index` equal to the configured concrete fixture index, unchanged `_source` and count equal to found expected IDs. Reject unknown/mutated/aliased documents with `fixture_dataset_drift`. Create only missing IDs with `op_type=create` and `refresh=wait_for`; never overwrite, delete or reset existing documents. Re-read count + exact IDs/full source after seeding. A previous partial timeout can recover from missing documents only if every remaining document already matches the canonical fixture. An external same-index writer can still race between checks; the second check detects many such races but this is **not an ES transaction** or a cross-host lock.

On **Linux**, a 0700 UID-owned directory under the process temporary root and 0600 no-follow regular lock file provide a nonblocking `flock` per canonical project path. An authenticated concurrent operator preflight in another process on the **same host/lock directory** receives HTTP 409 before touching LLM/ES or changing local generation. The file lock persists while a blocking SDK still holds the server handler; kernel FD closing on process death releases it. Unsafe, unreadable or uncreatable lock files fail closed with sanitized HTTP 503 `external_e2e_host_guard_unavailable`. This guard does not signal, kill or preempt the provider.

The existing superuser `GET /v1/operator-e2e/runtime-evidence/status` remains **local**. If this process has no active preflight but observes the host lock held, it reports `HOST_LOCK_HELD`, `generation=0`, `elapsed_seconds=0`, `scope=linux_same_host_lock_observation_only`; no cross-process PID, owner, result or acceptance is inferred. An unavailable lock returns sanitized 503. Local tracker states and generation remain as in #323/#324. Non-Linux environments retain the previous process-local behavior. This is advisory locking on one Linux filesystem, not shared distributed coordination, durable job state, or multi-process backend-plan propagation; each worker still has its own immutable plan. Real Linux/model/ES end-to-end tests require separate authorization.


## 2026-10-30 Provisional E2E BackendPlan publication (post-#325)

The authenticated operator runtime-evidence handler now enters a **request-local staging context** inside the existing cooperative 540-second budget. `frozen_plan(resolve_environment_plan)` may compute a candidate before the complete evidence handler finishes, but **does not install a previously absent process-wide E2E plan until the handler returns successfully within budget**. The candidate is visible only in that request ContextVar; other request threads and E2E Report Jobs reject an unprepared plan rather than using an unverified live or mock backend. A late provider, later runtime-evidence exception, root/source failure or deadline exhaustion discards the provisional candidate, preserves the existing `FAILED`/`TIMEOUT` status and releases the Linux host guard on server-side exit. An authorized retry may revalidate the dedicated ES fixture, using #325 exact-source/create-only logic.

This is an **operator-handler commit boundary**, *not* an atomic external ES mutation, a hard SDK cancellation, a lasting acceptance receipt, a cross-process shared BackendPlan or a multi-host coordinator. Already-published process-local plans are immutable under the existing contract and are **not revoked by an unsuccessful later status request**; strict revalidation, durable plan identity and authorized production deployment remain distinct future work. Non-HTTP direct callers of `frozen_plan` retain their existing immediate publication semantics for compatibility; production Report Jobs do not gain an E2E plan from this change. No new CLI flag, API endpoint, model timeout or production startup action is added.
