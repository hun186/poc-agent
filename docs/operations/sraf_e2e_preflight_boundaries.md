# SRAF operator E2E capability preflight — request boundaries

The existing authenticated superuser `GET /v1/operator-e2e/runtime-evidence` explicitly prepares and freezes the E2E backend plan. It is NOT part of normal FastAPI startup or a safe anonymous health check. It may contact real LLM servers, inspect or seed the dedicated E2E Elasticsearch fixture and should only be executed with operator authorization.

For `REQUIREMENT_E2E_EXTERNAL_MODE=live` and `auto`, direct Router/Report/Refiner probes already send a short READY request with a 10s client timeout. The Data Agent boundary uses a separate smolagents LiteLLMModel READY call with **`timeout=30`, `num_retries=0`**; these arguments are only for E2E capability selection, not production report generation. An unavailable boundary is a redacted probe failure: `live` rejects the plan; `auto` may freeze the documented semantic-mock E2E fallback, and that fallback must NEVER affect production jobs. `offline` does not send live model probes.

**Operator HTTP client wait:** On a supported Linux main-thread E2E harness run, the authenticated runtime-evidence GET now has an independent **600-second elapsed-time SIGALRM/ITIMER_REAL limit**, including slow-drip response bodies. If it expires, the harness records the fixed `remote_preflight_client_deadline_exceeded` error in `RUNTIME_WORKERS`; it never retries the GET or emits secrets. The original Requests timeout still governs individual network operations. The operator harness refuses to send this GET if SIGALRM is already owned by another handler/timer or called from a Linux non-main thread. On other platforms (including remote-mode Windows), the previous Requests 600-second inactivity timeout remains; there is no portable absolute guard. This change does not cover later E2E API calls.

**Limitations:** This client-side absolute limit stops *the operator waiting*, not the API server's already-running synchronous preflight, model calls or ES fixture activity. The server might finish after the client has failed; never interpret a client timeout as server cancellation, absence of ES writes or a new plan install. An operator should not immediately retry without checking deployment runtime state. No universal, cancellation-safe whole-operation timeout exists yet. Other ES and model operations may take additional time and eventual network cancellation is provider-dependent. No private Linux busy-Ollama preflight, Report Job, Agent, SQL/ES or DOCX acceptance was performed in GitHub Hosted CI. Operators must keep the normal, nonmutating baseline separate from E2E preflight and must not auto-run live fixture setup as diagnostics.
